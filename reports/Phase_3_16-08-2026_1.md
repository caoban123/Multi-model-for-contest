## Data / API Contract

Visual `/api/search` returns:

- `raw_results`: candidate frames before aggregation; raw rank and score are not changed.
- `results`: backward-compatible frame diversity output.
- `video_results`: Top-K unique videos for the Phase-3 main UI.
- `video_groups`: compatibility alias for `video_results`.

`VideoResult` fields:

```text
rank
video_id
group
video_score
best_score
best_keyframe_id
best_frame_idx
best_pts_time
best_keyframe_path
frame_count
matched_frame_count
aggregation_method
frames
```

`frame_count` is the number of this video's frames in the candidate pool. `matched_frame_count` is the number attached to the API result after the display limit. Matched frames are ordered by score descending. Timeline neighbors are ordered by `pts_time` ascending and do not receive fabricated retrieval scores.

Defaults:

```text
top_k_videos = 12
candidate_pool_size = 40
aggregation_method = max
max_frames_per_video = 1
matched_frames_per_video = 5
neighbor_radius = 3
mean_top_n = 3
```

## Risks

- `frame_count` depends on candidate-pool size; comparisons must use the same Pool.
- A small Pool may contain fewer than K unique videos, so Video Ranking can legitimately return fewer than K cards.
- Manual relevance may reveal that increased diversity exposes more low-relevance videos; this is not measurable until P3-002 closes.
- A backend process started before these edits must be restarted; otherwise it still serves the old in-memory API schema.
- Current local image coverage must not be generalized to other team machines.
